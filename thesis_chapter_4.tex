\section{Dataset Generation Implementation}

Our dataset generation system is implemented as a modular, extensible framework that supports both template-based and random-walk approaches to create comprehensive NL2SPARQL datasets. This section details the technical implementation of each component, their interactions, and domain-specific adaptations for the university curriculum, legal, and GESIS knowledge graphs.

\subsection{System Architecture Overview}

The dataset generation system consists of five main components that work together to produce high-quality NL2SPARQL datasets:

\begin{enumerate}
    \item \textbf{Knowledge Graph Schema Extractor}: Analyzes the knowledge graph to identify classes, properties, entity examples, and type relationships
    
    \item \textbf{Vector Search Engine}: Provides semantic search capabilities for entity and property matching using Weaviate and sentence embeddings
    
    \item \textbf{Template-Based Generator}: Creates linguistically diverse questions with corresponding SPARQL queries using a discovery-first approach
    
    \item \textbf{Random-Walk Generator}: Discovers structural patterns in the knowledge graph to ensure comprehensive coverage of query patterns
    
    \item \textbf{Post-Processing Pipeline}: Standardizes SPARQL query formats, enhances dataset with LLM-generated content, and prepares final training/testing splits
\end{enumerate}

The implementation follows a modular design pattern where each component is implemented as a separate Python class with well-defined interfaces, enabling flexible combination and domain-specific customization.

\subsection{Query Optimization for Large Knowledge Graphs}
\label{query-optimization}

A critical aspect of our dataset generation implementation is the optimization of SPARQL queries, particularly when working with large knowledge graphs such as GESIS KG. Query performance can significantly impact the efficiency of the dataset generation process, especially during the discovery-first instantiation phase where multiple queries need to be executed to find valid entity-property combinations.

\subsubsection{Triple Pattern Ordering}

We discovered that the order of triple patterns within SPARQL queries can dramatically affect execution time. Consider the following example from our work with the GESIS Knowledge Graph (before modification):

\begin{lstlisting}[language=SPARQL, caption=Original query - execution time: 2.155 seconds]
SELECT ?authorName WHERE {
  ?author schema:name ?authorName .
  ?publication schema:author ?author .
}
GROUP BY ?author ?authorName
ORDER BY DESC(COUNT(?publication))
LIMIT 1
\end{lstlisting}

By simply reordering the triple patterns, we achieved a significant performance improvement:

\begin{lstlisting}[language=SPARQL, caption=Reordered query - execution time: 0.698 seconds]
SELECT ?authorName WHERE {
  ?publication schema:author ?author .
  ?author schema:name ?authorName .
}
GROUP BY ?author ?authorName
ORDER BY DESC(COUNT(?publication))
LIMIT 1
\end{lstlisting}

This performance difference occurs because of how SPARQL query execution engines process the patterns. In the first query, \texttt{?author schema:name ?authorName} instantiates all entities with a name property, including many that aren't actually authors. This creates a large intermediate result set that must then be filtered by the second triple pattern.

In contrast, the reordered query first identifies publications and their authors with \texttt{?publication schema:author ?author}, creating a much smaller intermediate result set of only actual authors, before retrieving their names. This pattern ordering ensures that we don't instantiate unnecessary triples during query execution.

\subsubsection{Query Structure Optimization}

We implemented further optimizations by restructuring queries to minimize redundant operations. For example, we can enhance the previous query by moving the \texttt{schema:name} property retrieval outside of the grouping operation:

\begin{lstlisting}[language=SPARQL, caption=Fully optimized query with nested structure]
SELECT ?authorName WHERE {
  {
    SELECT ?author WHERE {
      ?publication schema:author ?author .
    }
    GROUP BY ?author
    ORDER BY DESC(COUNT(?publication))
    LIMIT 1
  }
  ?author schema:name ?authorName .
}
\end{lstlisting}

This structure ensures that we only retrieve the name for the single author with the largest number of publications, rather than retrieving names for all authors before filtering. This optimization is particularly valuable when working with large knowledge graphs containing millions of entities.

\subsubsection{Validation and Performance Monitoring}

To systematically identify and address performance issues in our query templates, we implemented a comprehensive query validation and execution monitoring system. Rather than relying on an automated optimization function, we developed a manual optimization workflow using our \texttt{validate\_gesis\_sparql.py} script:

This script allows us to run all generated queries against the target knowledge graph and identify those that exceed our performance threshold (typically 2 seconds). When slow queries are identified, we manually analyze them to determine the cause of the performance issue and apply appropriate optimizations:

\begin{enumerate}
    \item Reordering triple patterns to prioritize selective patterns first
    \item Restructuring queries with nested subqueries to optimize operations
    \item Removing unnecessary graph patterns that don't contribute to the result
    \item Adding explicit type constraints to limit intermediate result size
\end{enumerate}

The manual optimization approach, while more labor-intensive than an automated system, ensures that each template in our dataset generation system produces efficient queries that can be executed reliably against large knowledge graphs. This was particularly important for the GESIS Knowledge Graph, which contains millions of triples describing scholarly publications, authors, and related metadata.

By systematically identifying and optimizing slow-performing queries, we significantly improved the overall efficiency of our dataset generation process, reducing the average query execution time by approximately 60\% across our template library.

\subsubsection{N-gram Processing Implementation}

We implemented n-gram processing to break down natural language questions into searchable chunks, enabling more effective matching with knowledge graph elements. The implementation is shown below:

\begin{lstlisting}[breaklines=true,language=python, caption=N-gram Processing Implementation]
def _preprocess_into_tokens(self, q: str) -> list[str]:
    """
    Preprocess question into tokens using NLTK RegexpTokenizer
    
    Args:
        q (str): Question string
        
    Returns:
        list[str]: List of tokens
    """
    tok_pattern = r"\w+"
    tokenizer = RegexpTokenizer(tok_pattern)
    tokenized = tokenizer.tokenize(q)
    result = []
    for tok in tokenized:
        tok = tok.lower()
        if tok not in self.stopwords:
            result.append(tok)
    return result

def _generate_ngrams(self, tokens: list[str], max_n: int = 3) -> list[str]:
    """
    Generate n-grams from tokens using NLTK
    
    Args:
        tokens (list[str]): List of tokens
        max_n (int): Maximum n-gram size
        
    Returns:
        list[str]: List of n-grams
    """
    result = []
    
    # Generate unigrams, bigrams, and trigrams using NLTK
    for n in range(1, min(max_n + 1, len(tokens) + 1)):
        n_grams = ngrams(tokens, n)
        result.extend([" ".join(ng) for ng in n_grams])
    
    return result
\end{lstlisting}

    thoughts_formatted = "Let me analyze this step by step:\n\n"
    for i, thought in enumerate(row['thoughts'], 1):
        thoughts_formatted += f"{thought}\n"
    
    asst_prompt = f"""{thoughts_formatted}

```sparql
{row['sparql']}
```"""

    if has_chat_template:
        prompt = tokenizer.apply_chat_template(
            [
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": user_prompt},
                {"role": "assistant", "content": asst_prompt}
            ],
            tokenize=False,
            add_generation_prompt=False,
            continue_final_message=False
        )
    else:
        prompt = system_prompt + '\n' + user_prompt + '\n' + asst_prompt
    
    return prompt
\end{lstlisting}

Our implementation carefully handles model-specific chat templates, ensuring that examples are properly formatted for each model's expected input format. For models without native chat templates, we apply appropriate formatting to maintain consistency.

\subsection{Implementation Challenges and Solutions}

Throughout the implementation process, we encountered and addressed several technical challenges:

\begin{enumerate}
    \item \textbf{Memory Limitations}: We addressed GPU memory constraints through aggressive optimization techniques including 4-bit quantization, gradient checkpointing, and memory-efficient optimizers. The complete implementation is provided in \hyperref[code:memory-optimization]{Appendix~\ref{sec:implementation-code}}.
    
    \item \textbf{Model Compatibility}: Each model family required specific adaptations to ensure compatibility with our training approach. We implemented model-specific chat template handling and tokenization to ensure consistent behavior, especially for \texttt{Qwen/Qwen2.5-7B-Instruct} where it doesn't have its own chat template. The complete implementation is provided in \hyperref[code:model-compatibility]{Appendix~\ref{sec:implementation-code}}.
    
    \item \textbf{Training Stability}: Higher-rank QLoRA configurations occasionally experienced training instabilities, particularly for SPARQL generation. We implemented rank-stabilized QLoRA (RSQLoRA) to address this issue. The complete implementation is provided in \hyperref[code:training-stability]{Appendix~\ref{sec:implementation-code}}.
        
    \item \textbf{Component Initialization Order}: We discovered critical incompatibilities between Unsloth and Weaviate when both were initialized in the same Python process. Specifically, Unsloth's CUDA optimizations conflicted with Weaviate's GPU memory management. This required careful implementation sequencing where Weaviate client initialization had to be performed after all Unsloth fine-tuning processes were completed. The complete implementation is provided in \hyperref[code:initialization-order]{Appendix~\ref{sec:implementation-code}}.

    This ordering constraint required careful restructuring of our pipeline to separate fine-tuning and inference phases completely.

    \item \textbf{Package Dependency Instability}: A significant challenge was managing package dependencies with rapidly evolving libraries. For example, we discovered that langchain-huggingface $\geq$ 0.2.0 introduced breaking changes that were incompatible with our Unsloth implementation. The complete implementation is provided in \hyperref[code:dependency-issue]{Appendix~\ref{sec:implementation-code}}.
    
    To address this, we had to explicitly pin langchain-huggingface to version 0.1.2 in our installation requirements. Without such version pinning, the same code would fail when dependencies received updates, highlighting the fragility of deep learning pipelines that rely on multiple rapidly evolving libraries.
    
    Additionally, we found that the \texttt{protobuf} package version was critical for compatibility between Weaviate and our model processing pipeline. The version needed to be specifically upgraded with the command \texttt{pip install --upgrade -q protobuf} to prevent serialization errors when moving between the fine-tuning and vector database components of our system.
    
    \item \textbf{Tokenizer Inconsistencies}: We encountered issues where tokenizers initialized differently across model runs, particularly with the Qwen2.5 models. This required explicit chat template verification and setting even when the documentation suggested it should be automatically loaded. The complete implementation is provided in \hyperref[code:tokenizer-verification]{Appendix~\ref{sec:implementation-code}}.
    
    \item \textbf{Resource Deallocation}: Proper resource deallocation became critical for the stability of our pipeline. We found that standard Python garbage collection was insufficient, and explicit model deletion and CUDA cache clearing were necessary between processing stages:

    \begin{lstlisting}[breaklines=true,language=python, caption=Resource Deallocation Implementation, label=code:resource-deallocation]
    def clean_model_resources():
        """Aggressive resource cleanup between model loads"""
        # Delete model explicitly
        if 'model' in globals():
            del globals()['model']
        
        # Delete tokenizer explicitly 
        if 'tokenizer' in globals():
            del globals()['tokenizer']
        
        # Clear CUDA cache with synchronization
        torch.cuda.empty_cache()
        if torch.cuda.is_available():
            torch.cuda.synchronize()
        
        # Force garbage collection multiple times
        for _ in range(3):
            gc.collect()
    \end{lstlisting}
\end{enumerate}

These implementation challenges highlight the complexity of building production-ready systems that integrate multiple deep learning and vector database components. Our solutions ensured reproducible behavior across different environments while maintaining the performance benefits of our optimized approach.

The visualizer maintains an in-memory log of execution events, capturing detailed information about each step in the agent's processing pipeline. This information includes:

Events are captured through the \texttt{log\_event} method, which is called by each agent node during execution:

\begin{lstlisting}[language=python, caption=Event logging implementation, label=code:event-logging]
def log_event(self, component, event_type, details=None, start_time=None, end_time=None):
    """Log a process event with timestamp"""
    if self.verbose < 1:
        return
        
    timestamp = datetime.now()
    log_entry = {
        "component": component,
        "event_type": event_type,
        "details": details,
        "timestamp": timestamp.isoformat(),
        "start_time": start_time.isoformat() if start_time else None,
        "end_time": end_time.isoformat() if end_time else None
    }
    
    self.logs.append(log_entry)
    
    # If debug_callback is provided, send the log entry through it
    if self.debug_callback:
        debug_msg = f"{component} - {event_type}"
        if details:
            debug_msg += f"\nDetails: {json.dumps(details, cls=CustomEncoder, indent=2)}"
        
        if start_time and end_time:
            duration = (end_time - start_time).total_seconds()
            debug_msg += f"\nDuration: {duration:.3f}s"
        
        # Handle asynchronous callbacks
        if asyncio.iscoroutinefunction(self.debug_callback):
            try:
                loop = asyncio.get_event_loop()
                if loop.is_running():
                    future = asyncio.run_coroutine_threadsafe(self.debug_callback(debug_msg), loop)
                    # Optionally wait for result with timeout
                    try:
                        future.result(timeout=1.0)
                    except Exception as e:
                        print(f"Error in async callback: {e}")
                else:
                    loop.run_until_complete(self.debug_callback(debug_msg))
            except RuntimeError:
                # No event loop in this thread, create a new one
                loop = asyncio.new_event_loop()
                asyncio.set_event_loop(loop)
                loop.run_until_complete(self.debug_callback(debug_msg))
        else:
            # Regular synchronous callback
            try:
                self.debug_callback(debug_msg)
            except Exception as e:
                print(f"Error in callback: {e}")
\end{lstlisting}

\subsubsection{SPARQL Query Examples}
Our Apache Jena integration enables a wide range of analytical queries on the execution logs. Below are some example queries that demonstrate the power of the semantic logging approach:

\begin{lstlisting}[language=sparql, caption=SPARQL query for listing all runs with timestamps, label=code:sparql-runs]
SELECT ?run ?startTime ?endTime ?duration ?totalEvents
WHERE {
  ?run rdf:type logex:ConversionMetadata ;
       logex:startTime ?startTime ;
       logex:endTime ?endTime ;
       logex:totalDuration ?duration ;
       logex:totalEvents ?totalEvents .
} 
ORDER BY DESC(?startTime)
\end{lstlisting}

\begin{lstlisting}[language=sparql, caption=SPARQL query for finding runs with specific entities, label=code:sparql-entities]
SELECT DISTINCT ?run ?entityLabel ?startTime
WHERE {
  ?event log:hasEntity ?entity .
  ?event logex:belongsToRun ?run .
  ?entity rdfs:label ?entityLabel .
  ?run logex:startTime ?startTime .
  
  # Filter for specific entity (remove or change this filter as needed)
  FILTER(CONTAINS(LCASE(?entityLabel), "ma huateng"))
}
ORDER BY DESC(?startTime)
\end{lstlisting}

\begin{lstlisting}[language=sparql, caption=SPARQL query for finding SPARQL queries used in runs, label=code:sparql-queries]
SELECT ?run ?queryText ?startTime
WHERE {
  ?event log:hasQuery ?query .
  ?event logex:belongsToRun ?run .
  ?query rdfs:label ?queryText .
  ?run logex:startTime ?startTime .
}
ORDER BY DESC(?startTime)
\end{lstlisting}

\begin{lstlisting}[language=sparql, caption=SPARQL query for analyzing approach distribution, label=code:sparql-approaches]
SELECT ?approach (COUNT(?event) as ?count)
WHERE {
  ?event log:approach ?approach .
}
GROUP BY ?approach
ORDER BY DESC(?count)
\end{lstlisting}

\begin{lstlisting}[language=sparql, caption=SPARQL query for calculating average duration by component, label=code:sparql-duration]
SELECT ?component (AVG(?duration) as ?avgDuration) (COUNT(?event) as ?count)
WHERE {
  ?event log:pname ?componentUri ;
         log:duration ?duration .
  BIND(STRAFTER(STR(?componentUri), "log#") as ?component)
}
GROUP BY ?component
ORDER BY DESC(?avgDuration)
\end{lstlisting}

\begin{lstlisting}[language=sparql, caption=SPARQL query for finding most common entities, label=code:sparql-common-entities]
SELECT ?entityLabel (COUNT(?entity) as ?count)
WHERE {
  ?event log:hasEntity ?entity .
  ?entity rdfs:label ?entityLabel .
}
GROUP BY ?entityLabel
ORDER BY DESC(?count)
LIMIT 20
\end{lstlisting}

\begin{lstlisting}[language=sparql, caption=SPARQL query for finding most common Wikidata properties, label=code:sparql-common-properties]
SELECT ?propertyId (COUNT(?property) as ?count)
WHERE {
  ?query log:referencesProperty ?property .
  ?property log:wikidataId ?propertyId .
}
GROUP BY ?propertyId
ORDER BY DESC(?count)
LIMIT 20
\end{lstlisting}

\section{Computational Setup}
\label{sec:computational-setup}

This section details the hardware specifications, deployment configurations, and interconnectivity of the various components in our implementation. The computational setup employs a distributed architecture across multiple devices, with services interconnected through both local network and cloud-based solutions.

\subsection{Hardware Environment}
The implementation is distributed across two identical devices, both MacBook Pro M3 models with 18GB unified memory. The distribution of components was designed to balance computational load while ensuring reliable performance:

\begin{itemize}
    \item \textbf{Device 1}: Hosts the Django backend with multi-agent system and Ollama for local model inference
    \item \textbf{Device 2}: Hosts supporting infrastructure including Weaviate vector database and Apache Jena Fuseki
\end{itemize}

\subsection{Frontend Deployment}
The React frontend is deployed through Vercel's continuous deployment pipeline, which is directly connected to the GitHub repository. This setup provides automatic builds and deployments whenever changes are pushed to the web branch:

\begin{itemize}
    \item \textbf{Repository Path}: \texttt{https://github.com/gansixeneh/FROG-2.0/tree/web} in the \texttt{wikidata-chat/frontend} folder
    \item \textbf{Deployment Platform}: Vercel with GitHub integration for continuous deployment
    \item \textbf{Build Configuration}: Automatic builds triggered by commits to the web branch
\end{itemize}

This approach ensures that the frontend is always synchronized with the latest codebase while providing robust hosting and content delivery capabilities.

\subsection{Backend Infrastructure}
The backend implementation runs locally on Device 1 and is made accessible to the Internet through ngrok, which provides a secure tunnel to the locally running Django application.

\begin{itemize}
    \item \textbf{Django Server}: Runs locally on Device 1, providing the REST API and WebSocket endpoints
    \item \textbf{Ngrok Tunnel}: Utilizes ngrok's free tier static domain feature\footnote{\url{https://ngrok.com/blog-post/free-static-domains-ngrok-users}} to provide a consistent public URL for frontend communication
    \item \textbf{Ollama Provider}: Runs locally on Device 1 with the command \texttt{ollama serve}, exposing the API on \texttt{localhost:11434} for local model inference
\end{itemize}

This setup enables the locally running backend to be securely exposed to the Internet without requiring dedicated hosting infrastructure, while the Ollama provider allows local execution of fine-tuned models without relying on external APIs.

\subsection{Pusher Integration}
For real-time communication between the frontend and backend, we utilize Pusher's WebSocket infrastructure. The implementation uses Pusher's free tier, which provides:

\begin{itemize}
    \item 200,000 messages per day
    \item 100 concurrent connections
    \item Real-time event broadcasting and channel subscription
\end{itemize}

Pusher serves as the bridge between the frontend deployed on Vercel and the backend running locally behind ngrok, enabling real-time updates during the multi-agent execution process.\footnote{\url{https://pusher.com/channels/pricing/}}

The decision to use Pusher as an intermediary WebSocket service was necessitated by Vercel's stateless serverless architecture, which limits WebSocket connections to approximately one minute before timing out. Since our multi-agent system often requires longer processing times for complex queries, a direct WebSocket connection through Vercel would be insufficient. Pusher resolves this limitation by providing a persistent connection infrastructure that bridges the stateless Vercel frontend with our long-running backend processes.

\subsection{Weaviate Vector Database}
The Weaviate vector database is deployed on Device 2 using Docker Compose with the following configuration:

\begin{lstlisting}[breaklines=true,language=yaml, caption=Weaviate Docker Compose Configuration]
services:
  weaviate:
    image: semitechnologies/weaviate:latest
    ports:
      - "${WEAVIATE_HTTP_PORT:-8080}:8080"
      - "${WEAVIATE_GRPC_PORT:-50052}:50051"
    environment:
      QUERY_DEFAULTS_LIMIT: 20
      AUTHENTICATION_ANONYMOUS_ACCESS_ENABLED: 'true'
      PERSISTENCE_DATA_PATH: '/var/lib/weaviate'
      DEFAULT_VECTORIZER_MODULE: 'none'
      ENABLE_MODULES: ''
      CLUSTER_HOSTNAME: 'node1'
    volumes:
      - weaviate_data:/var/lib/weaviate
volumes:
  weaviate_data:
\end{lstlisting}

The configuration exposes Weaviate on the default ports (8080 for HTTP and 50052 for gRPC) and enables persistent storage through a Docker volume. The backend on Device 1 connects to Weaviate on Device 2 using the local network IP address within the same WiFi network.

\subsection{Apache Jena Fuseki}
The Apache Jena Fuseki semantic web server is also deployed on Device 2, running on its default port (3030). This server provides SPARQL query capabilities for the RDF-based logging system, enabling sophisticated analysis of agent execution patterns.
